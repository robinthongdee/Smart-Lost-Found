# Smart Lost & Found

เว็บจับคู่ของหาย–ของที่พบในมหาวิทยาลัย ผู้ใช้แจ้งของหายหรือของที่พบ ระบบแนะนำรายการที่อาจตรงกัน และให้ AI ช่วยประเมินความตรงของสองรายการพร้อมเหตุผล

## ปัญหาและผู้ใช้ (ต้องเติมเอง)
- ปัญหา: ของหายในมหาวิทยาลัยตามหาไม่ได้ เพราะประกาศกระจัดกระจายหลายช่องทาง
- กลุ่มผู้ใช้: นักศึกษาและบุคลากร
- หลักฐานจากผู้ใช้จริง: ใส่ผลแบบสอบถาม/สัมภาษณ์ของคุณที่นี่ (จำนวนผู้ตอบ สาเหตุที่พบ ผลกระทบ)

## AI ทำงานยังไง
ระบบแบบ 2 ชั้น
1. **กฎ (ฝั่งเบราว์เซอร์)** คัดรายการที่อาจตรง: คนละชนิด (หาย/พบ) + ประเภทเดียวกัน + สถานที่เดียวกันหรือชื่อมีคำซ้ำกัน เร็วและไม่มีค่าใช้จ่าย
2. **AI (ฝั่งเซิร์ฟเวอร์ `api/match.js`)** เมื่อผู้ใช้กด "🤖 ให้ AI ตรวจ" ในหน้าแจ้งเตือน โมเดล Google Gemini (ค่าเริ่มต้น `gemini-3.5-flash-lite` เปลี่ยนได้ด้วย `AI_MODEL`) เปรียบเทียบสองรายการแล้วคืน JSON
   - `score` 0–100
   - `verdict`: `match` / `maybe` / `no_match` / `insufficient` (ข้อมูลไม่พอ) / `out_of_scope` (ไม่ใช่ข้อมูลของหาย/ของที่พบ)
   - `reason` เหตุผลภาษาไทยสั้น ๆ
   - `missing` รายละเอียดที่ควรเพิ่ม (ใช้ตอนข้อมูลไม่พอ)

**การออกแบบ prompt เพื่อให้ผลนิ่งและไม่มั่นใจเกินจริง**
- ส่งข้อมูลเรียงลำดับตายตัว (`item_a` = ของหาย, `item_b` = ของที่พบ) ไม่ว่าใครกดตรวจ เพื่อให้ผลสม่ำเสมอ
- ตั้ง `temperature = 0` และบังคับให้ตอบเป็น JSON
- ถ้าทั้งสองรายการมีแค่ชื่อหรือรุ่นทั่วไป ไม่มีรายละเอียดแยกแยะ (สี ตำหนิ พวงกุญแจ หมายเลข) คะแนนต้องไม่เกิน 70 และไม่ตอบ `match` พร้อมบอกว่าควรเพิ่มอะไร
- สถานที่ต่างกันแต่รายละเอียดวัตถุตรงกัน หักคะแนน 10–15 ไม่ตัดเป็น `no_match`
- ฝั่งเซิร์ฟเวอร์ตรวจให้คะแนนสอดคล้องกับ verdict โดยให้คะแนนของโมเดลเป็นตัวตัดสิน ถ้าโมเดลตอบ `match` แต่คะแนนต่ำกว่า 75 จะลดระดับ verdict เป็น `maybe` (หรือ `no_match` ถ้าต่ำกว่า 40) ส่วน `no_match` ไม่เกิน 39, `insufficient` ไม่เกิน 70, `out_of_scope` = 0

**ความเร็วและความเสถียร (เป้าหมายเฉลี่ยไม่เกิน 10 วินาที)**
- รอ Gemini ครั้งแรกไม่เกิน 5 วินาที ถ้าช้ากว่านั้นหรือเจอ error 500/503 จะลองใหม่อีก 1 ครั้ง (รอไม่เกิน 6 วินาที) กรณีแย่สุดรวมประมาณ 12 วินาที
- ถ้าเจอ 429 (โควตาต่อนาทีเต็ม) จะไม่ลองซ้ำ และแจ้งผู้ใช้ให้รอแล้วกดใหม่ เพราะการลองซ้ำใช้โควตาเพิ่ม
- จำกัดความยาวคำตอบ (`maxOutputTokens` = 400) และตั้ง `thinkingLevel` เป็น `low`
- หน้าเว็บจัดคิวคำขอทีละรายการ เว้น 3.5 วินาที (กันชนโควตา Gemini 15 คำขอต่อนาที) และกันการกดซ้ำคู่เดียวกัน ระหว่างรอแสดง "รอคิว…" และ "กำลังประมวลผล…"
- ผลทดสอบจริง 20 ครั้ง (5 คู่ × 4 รอบ) เวลาเฉลี่ยประมาณ 5.4 วินาที สูงสุด 9.3 วินาที

**ทำไมใช้ AI:** คำบรรยายของหายเป็นข้อความอิสระภาษาไทย เช่น "เคสสีฟ้า" กับ "ปกสีน้ำเงิน" กฎคีย์เวิร์ดจับไม่ได้ AI เข้าใจความหมายและบอกเหตุผลได้
**ทางเลือกอื่น:** จับคู่คีย์เวิร์ด (มีอยู่แล้วเป็นชั้นแรก), embedding similarity (แม่นกว่าคีย์เวิร์ด แต่ไม่อธิบายเหตุผลและต้องมีที่เก็บเวกเตอร์เพิ่ม)
**ข้อจำกัด:** AI อาจผิดพลาด จึงแสดงเป็นคำแนะนำและเตือนให้ตรวจสอบกับอีกฝ่ายก่อนส่งมอบของ ถ้าผู้ใช้ใส่รายละเอียดน้อย ระบบจะให้คะแนนกลางและขอรายละเอียดเพิ่ม ไม่ฟันธงว่าตรงกัน

## ความปลอดภัย
- API key ของ AI (`GEMINI_API_KEY`) อยู่ใน Environment Variable บน Vercel เท่านั้น ไม่อยู่ในโค้ดหน้าเว็บหรือ repository
- คีย์ `sb_publishable_...` ของ Supabase ออกแบบมาให้เปิดเผยได้ ความปลอดภัยของข้อมูลอยู่ที่ Row Level Security ของ Supabase
- `/api/match` ต้องมี token ผู้ใช้ Supabase (รวมบัญชีไม่ระบุตัวตน) ไม่ใช่ endpoint เปิดสาธารณะ
- กัน prompt injection: ข้อความผู้ใช้ถูกครอบเป็น JSON ในแท็กและ escape เครื่องหมาย `<` system prompt สั่งให้ถือเป็นข้อมูลเท่านั้น ผลลัพธ์ถูกบังคับเป็น JSON และตรวจ schema ก่อนส่งกลับ
- จำกัดความยาวข้อความและชนิดไฟล์รูปทั้งฝั่งหน้าเว็บและเซิร์ฟเวอร์ รูปถูกย่อไม่เกิน 800 px ก่อนบันทึก

## PDPA
- ฟอร์มมีช่องติ๊กยินยอมก่อนบันทึก และลิงก์นโยบายความเป็นส่วนตัวทุกหน้า
- ส่งให้ AI เฉพาะชื่อ ประเภท สถานที่ เวลา รายละเอียด (ไม่ส่งช่องทางติดต่อ รูป อีเมล) จึงแนะนำผู้ใช้ไม่ให้ใส่เบอร์โทรหรือ LINE ในช่องรายละเอียด
- เมื่ออัปเดตเป็น "คืนแล้ว" รายการถูกลบออกจากระบบ (ลดการเก็บข้อมูลเกินจำเป็น)
- แก้ `CONTACT_EMAIL` ใน `app.js` เป็นอีเมลผู้ดูแลระบบสำหรับขอลบ/แก้ไขข้อมูล

## ตั้งค่าก่อนใช้งาน
**Vercel** → Project → Settings → Environment Variables
- `GEMINI_API_KEY` = คีย์ของคุณ (จำเป็น)
- `AI_MODEL` = ชื่อโมเดลอื่น (ไม่บังคับ ค่าเริ่มต้น `gemini-3.5-flash-lite`)
- แล้ว Redeploy

**Supabase**
- Authentication → Providers → เปิด Email (และเปิด Anonymous sign-ins ไว้เหมือนเดิม)
- ถ้าจะเดโมเร็ว ปิด "Confirm email" ถ้าเปิดไว้ ผู้ใช้ต้องกดลิงก์ในอีเมลก่อนลงทะเบียนเสร็จ
- ตรวจ RLS ตาราง `items`: ทุกคนอ่านได้ แต่เพิ่ม/แก้/ลบได้เฉพาะแถวที่ `owner = auth.uid()`

## โครงสร้างไฟล์
- `index.html`, `style.css`, `app.js` หน้าเว็บ
- `api/match.js` ฟังก์ชัน AI ฝั่งเซิร์ฟเวอร์
- `vercel.json` ตั้งเวลาสูงสุดของฟังก์ชัน (30 วินาที)
- `TEST-CASES.md` ชุดทดสอบ 13 กรณี และข้อมูลตัวอย่าง 5 กรณี
- `USER-GUIDE.md` คู่มือการใช้งาน

## ข้อจำกัดที่ทราบ
- แจ้งเตือนอัปเดตเมื่อโหลดหน้าใหม่เท่านั้น (ไม่ใช่ realtime)
- "ค้างมากี่วัน" นับจากวันที่ของรายการ ไม่ใช่วันที่เปลี่ยนสถานะ
- ยังไม่มี rate limit ต่อผู้ใช้บน `/api/match` (มีแค่ต้องล็อกอิน) แนวทางแก้: จำกัดจำนวนครั้งต่อผู้ใช้ต่อชั่วโมง
- กฎชั้นแรกตัดคำด้วยช่องว่าง ชื่อภาษาไทยที่ไม่มีเว้นวรรคจะจับคู่ด้วยชื่อได้เฉพาะเมื่อประเภทและสถานที่ตรงกัน
- Gemini แบบฟรีจำกัด 15 คำขอต่อนาทีสำหรับโมเดลที่ใช้ ถ้ากด "ให้ AI ตรวจ" ถี่เกินอาจได้ error 429 หน้าเว็บจัดคิวทีละคำขอและกันกดซ้ำ ฝั่งเซิร์ฟเวอร์ลองซ้ำเฉพาะกรณี 500/503/ตอบช้า ถ้ายังไม่ได้จะแจ้งให้ลองใหม่ และยังแสดงผลจับคู่ตามกฎได้ ถ้าใช้งานจริงจำนวนมากควรเปิดบิลลิ่งเพื่อเพิ่มโควตา
- ถ้าข้อมูลของสองรายการมีรายละเอียดน้อย คะแนนอาจอยู่ใกล้เส้น 75 และสลับระหว่าง "ตรงมาก" กับ "อาจตรง" เมื่อประเมินซ้ำ (verdict ไม่เคยกลับด้านเป็น `no_match` ในการทดสอบ 20 ครั้ง) ผลจะนิ่งขึ้นเมื่อผู้ใช้ใส่รายละเอียดชัดเจน

## สิทธิ์ผู้ใช้ (Admin / User)
- **User** (รวมแบบไม่ระบุตัวตน): ดูรายการทั้งหมด แจ้งของ และแก้ไข/อัปเดตสถานะ/ลบได้เฉพาะรายการของตัวเอง
- **Admin**: แก้ไข อัปเดตสถานะ และลบได้ทุกรายการ และเห็นแท็บ Dashboard
- บังคับสิทธิ์ที่ฐานข้อมูลด้วย RLS (ไม่ใช่แค่ซ่อนปุ่มในหน้าเว็บ): รัน `admin-setup.sql` ใน Supabase SQL Editor แล้วเพิ่มอีเมลแอดมินในตาราง `admins`
- แอดมินต้องลงทะเบียน/เข้าสู่ระบบด้วยอีเมลที่ตรงกับตาราง `admins` (ยืนยันอีเมลแล้ว)
